# מאזן — גרסת הזכוכית הכהה (מעודכנת)

הגרסה הכהה עם כל היכולות שנוספו מאז: סריקת ברקוד, צילום מנה,
מעקב מים, רישום פעילות, וארבעה מסכים.

## מה שונה מהגרסה הכהה הראשונה

### טיפוגרפיה
* **פונט אחד — Rubik**, במקום Frank Ruhl Libre לכותרות + Heebo לגוף.
  ההיררכיה נבנית מגודל ומשקל, לא מהחלפת משפחה.
* **סולם קבוע** במשתני CSS: 12.5 / 13.5 / 15 / 17 / 19 / 22 / 28 / 46.
  אין יותר מספרים אקראיים כמו 13.5 באזור אחד ו‑14.5 באזור אחר.
* **גודל מינימלי עלה** — הטקסטים הקטנים ביותר היו 10.5px, עכשיו 12.5px.
* מספרים מוגדרים `tabular-nums`, כך שהם לא קופצים כשהערך משתנה.

## חשבון וסנכרון

### הגדרה חד־פעמית (אתה, לא המשתמשים)

1. פתח פרויקט חינמי ב‑supabase.com
2. SQL Editor → New query → הדבק את `schema.sql` → Run
3. Project Settings → API → העתק את שתי השורות לראש `cloud.js`:

```js
const SUPABASE_URL      = 'https://xxxxx.supabase.co';
const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
```

זהו. המשתמשים רואים רק אימייל וסיסמה.

**ה‑anon key אמור להיות בקוד.** הוא מפתח ציבורי מעצם הגדרתו. מה שמגן
על הנתונים היא מדיניות ה‑RLS ב‑`schema.sql`, שאוכפת במסד עצמו שכל
משתמש ניגש אך ורק לשורות שלו. את ה‑`service_role` key אסור לשים
בקוד לקוח בשום מצב — הוא עוקף RLS.

### אישור מייל

כברירת מחדל Supabase דורש אישור מייל בהרשמה. אם אתה רוצה שההרשמה
תהיה מיידית: Authentication → Providers → Email → כבה
`Confirm email`. הקוד מטפל בשני המצבים.

### מסך הפתיחה

בכניסה הראשונה נפתח תהליך בן שני שלבים: חשבון, ואז גיל/גובה/משקל/מטרה.
הוא מוצג פעם אחת ונשמר תחת המפתח `maazan:onboarded`.

טופס ההרשמה מבקש אימייל, סיסמה ואימות סיסמה. הבדיקות רצות בצד הלקוח
לפני כל קריאה לשרת: מבנה אימייל, אורך סיסמה של 6 תווים לפחות, והתאמה
בין שתי הסיסמאות. במצב כניסה שדה האימות נעלם.

* משתמש חוזר שנכנס לחשבון קיים מדלג על שלב הפרטים — הם נמשכים מהענן.
* יש קישור קטן «המשך בלי חשבון», כדי שמי שאין לו אינטרנט לא ייתקע
  מול קיר. למחיקה: הסר את `#obSkip` מ‑`index.html`.
* אם `SUPABASE_URL` ריק, שלב החשבון מדולג אוטומטית והאפליקציה
  עובדת מקומית.

## מאמן ומתאמן

### מה נוסף

ההרשמה בשלושה שלבים, בסדר הזה בדיוק: **חשבון** (אימייל וסיסמה),
ואז **זהות** (שם משתמש, שם תצוגה, מתאמן או מאמן), ואז **פרטים אישיים**.

הסדר לא שרירותי. בדיקת זמינות של שם משתמש היא קריאה למסד, והמסד דורש
סשן — אז אי אפשר לבדוק אותה לפני שהחשבון קיים. אם אישור מייל מופעל
בפרויקט, שלב הזהות פשוט מופיע בכניסה הראשונה אחרי האישור.

ההגנה מפני שם משתמש כפול היא המפתח הייחודי `profiles_username_key`
במסד, לא הבדיקה בלקוח. הבדיקה רק חוסכת למשתמש הודעת שגיאה.

* **מאמן** מקבל מסך «המתאמנים שלי»: חיפוש לפי שם משתמש או שם תצוגה,
  שליחת בקשת גישה, ורשימת המתאמנים המאושרים.
* **מתאמן** רואה במסך הפרופיל בלוק «בקשות מאמנים» ומאשר או דוחה כל בקשה,
  ויכול לבטל גישה שכבר אישר בכל רגע.
* אחרי אישור, המאמן רואה את יום המתאמן — קלוריות מול היעד, מאקרו,
  ורשימת המאכלים לפי ארוחות — עם רענון אוטומטי כל 20 שניות.

### איך זה מאובטח

הגישה **לא** נשענת על הקוד בדפדפן אלא על מדיניות RLS ב־`schema.sql`:

```sql
create policy "approved coach reads trainee" on public.app_data
  for select using (exists (
    select 1 from public.coach_links l
    where l.trainee_id = public.app_data.user_id
      and l.coach_id   = auth.uid()
      and l.status     = 'approved'));
```

שלוש תוצאות שנובעות מזה ישירות:

1. מאמן שלא אושר לא יקבל שורה אחת, גם אם ישנה את הקוד בדפדפן.
2. הגישה היא **קריאה בלבד** — אין שום מדיניות שמאפשרת למאמן לכתוב
   אצל המתאמן.
3. ברגע שהמתאמן לוחץ «ביטול גישה», הסטטוס עובר ל־`revoked` והקריאה
   הבאה נחסמת. אין צורך שהמאמן יסגור משהו.

**מה שכן חשוב לדעת:** אישור הוא הכל-או-כלום. מאמן מאושר קורא את כל
מפתחות ה־`app_data` של המתאמן — יומן, משקל, ופרטי הפרופיל. אם תרצה
הפרדה עדינה יותר, זה שינוי בסכימה: לפצל את המפתחות לרמות רגישות
ולסנן במדיניות לפי `key`.

טבלת `profiles` קריאה לכל משתמש מחובר, כי בלי זה אי אפשר לחפש לפי שם
משתמש. היא חושפת שם משתמש, שם תצוגה ותפקיד בלבד — לא נתוני תזונה.

### שדרוג ממסד קיים

`schema.sql` idempotent, אז פשוט הרץ אותו שוב ב-SQL Editor. הוא יוסיף את
`profiles` ו־`coach_links` ואת המדיניות החדשה בלי לגעת בנתונים הקיימים.
משתמש שנרשם לפני השינוי לא יופיע בחיפוש עד שייצור שם משתמש — הכי פשוט
לצאת ולהירשם מחדש, או להוסיף לו שורה ב־`profiles` ידנית.

## צ׳אט

לכל קישור מאושר יש שיחה. המאמן פותח אותה מרשימת המתאמנים או מתוך
התצוגה החיה; המתאמן פותח אותה מבלוק «בקשות מאמנים» במסך הפרופיל.

* ההודעות נטענות מחדש כל 5 שניות בזמן שהחלון פתוח, ורק החדשות נמשכות
  (`created_at=gt.<אחרונה>`), אז זו בקשה קטנה ולא טעינה מלאה.
* **קריאה** מותרת לשני הצדדים של הקישור גם אחרי ביטול גישה — היסטוריית
  שיחה לא נמחקת בלי שמישהו ביקש.
* **שליחה** מותרת רק כל עוד הקישור במצב `approved`. ברגע שהמתאמן מבטל,
  ההודעה הבאה נדחית ב-RLS, והאפליקציה מציגה «אין הרשאה לשלוח».

זה פולינג, לא Realtime. אם תרצה דחיפה מיידית במקום כל 5 שניות, Supabase
Realtime עושה את זה עם מנוי לטבלת `messages` — שינוי של כמה שורות
ב-`cloud.js` בלבד, בלי נגיעה בסכימה.

**שים לב:** את `schema.sql` צריך להריץ שוב, הוא מוסיף את טבלת `messages`
ואת המדיניות שלה.
