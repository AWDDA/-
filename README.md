# מאזן — גרסת הזכוכית הכהה (מעודכנת)

הגרסה הכהה עם כל היכולות שנוספו מאז: סריקת ברקוד, צילום מנה,
מעקב מים, רישום פעילות, וארבעה מסכים.

## מה שונה מהגרסה הכהה הראשונה

### טיפוגרפיה
* **פונט אחד — Rubik**, במקום Frank Ruhl Libre לכותרות + Heebo לגוף.
  ההיררכיה נבנית מגודל ומשקל, לא מהחלפת משפחה.
* **סולם קבוע** במשתני CSS: 12.5 / 13.5 / 15 / 17 / 19 / 22 / 28 / 46.
  אין יותר מספרים אקראיים כמו 13.5 באזור אחד ו‑14.5 באזור אחר.
* **גודל מינימלי עלה** — הטקסטים הקטנים ביותר היו 10.5px, עכשיו 12.5px.
* מספרים מוגדרים `tabular-nums`, כך שהם לא קופצים כשהערך משתנה.

הרצה מקומית: `python3 -m http.server 8080`.
העלאה: GitHub Pages, כרגיל. `CACHE` מקודם ל‑`maazan-glass-v3`.
צילום מנה דורש את `worker.js` ב‑Cloudflare Workers עם מפתח Anthropic.

## חשבון וסנכרון

### הגדרה חד־פעמית (אתה, לא המשתמשים)

1. פתח פרויקט חינמי ב‑supabase.com
2. SQL Editor → New query → הדבק את `schema.sql` → Run
3. Project Settings → API → העתק את שתי השורות לראש `cloud.js`:

```js
const SUPABASE_URL      = 'https://xxxxx.supabase.co';
const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
```

זהו. המשתמשים רואים רק אימייל וסיסמה.

**ה‑anon key אמור להיות בקוד.** הוא מפתח ציבורי מעצם הגדרתו. מה שמגן
על הנתונים היא מדיניות ה‑RLS ב‑`schema.sql`, שאוכפת במסד עצמו שכל
משתמש ניגש אך ורק לשורות שלו. את ה‑`service_role` key אסור לשים
בקוד לקוח בשום מצב — הוא עוקף RLS.

### אישור מייל

כברירת מחדל Supabase דורש אישור מייל בהרשמה. אם אתה רוצה שההרשמה
תהיה מיידית: Authentication → Providers → Email → כבה
`Confirm email`. הקוד מטפל בשני המצבים.

### מסך הפתיחה

בכניסה הראשונה נפתח תהליך בן שני שלבים: חשבון, ואז גיל/גובה/משקל/מטרה.
הוא מוצג פעם אחת ונשמר תחת המפתח `maazan:onboarded`.

טופס ההרשמה מבקש אימייל, סיסמה ואימות סיסמה. הבדיקות רצות בצד הלקוח
לפני כל קריאה לשרת: מבנה אימייל, אורך סיסמה של 6 תווים לפחות, והתאמה
בין שתי הסיסמאות. במצב כניסה שדה האימות נעלם.

* משתמש חוזר שנכנס לחשבון קיים מדלג על שלב הפרטים — הם נמשכים מהענן.
* יש קישור קטן «המשך בלי חשבון», כדי שמי שאין לו אינטרנט לא ייתקע
  מול קיר. למחיקה: הסר את `#obSkip` מ‑`index.html`.
* אם `SUPABASE_URL` ריק, שלב החשבון מדולג אוטומטית והאפליקציה
  עובדת מקומית.

## מאמן ומתאמן

### מה נוסף

ההרשמה בשלושה שלבים, בסדר הזה בדיוק: **חשבון** (אימייל וסיסמה),
ואז **זהות** (שם משתמש, שם תצוגה, מתאמן או מאמן), ואז **פרטים אישיים**.

הסדר לא שרירותי. בדיקת זמינות של שם משתמש היא קריאה למסד, והמסד דורש
סשן — אז אי אפשר לבדוק אותה לפני שהחשבון קיים. אם אישור מייל מופעל
בפרויקט, שלב הזהות פשוט מופיע בכניסה הראשונה אחרי האישור.

ההגנה מפני שם משתמש כפול היא המפתח הייחודי `profiles_username_key`
במסד, לא הבדיקה בלקוח. הבדיקה רק חוסכת למשתמש הודעת שגיאה.

* **מאמן** מקבל מסך «המתאמנים שלי»: חיפוש לפי שם משתמש או שם תצוגה,
  שליחת בקשת גישה, ורשימת המתאמנים המאושרים.
* **מתאמן** רואה במסך הפרופיל בלוק «בקשות מאמנים» ומאשר או דוחה כל בקשה,
  ויכול לבטל גישה שכבר אישר בכל רגע.
* אחרי אישור, המאמן רואה את יום המתאמן — קלוריות מול היעד, מאקרו,
  ורשימת המאכלים לפי ארוחות — עם רענון אוטומטי כל 20 שניות.

### איך זה מאובטח

הגישה **לא** נשענת על הקוד בדפדפן אלא על מדיניות RLS ב־`schema.sql`:

```sql
create policy "approved coach reads trainee" on public.app_data
  for select using (exists (
    select 1 from public.coach_links l
    where l.trainee_id = public.app_data.user_id
      and l.coach_id   = auth.uid()
      and l.status     = 'approved'));
```

שלוש תוצאות שנובעות מזה ישירות:

1. מאמן שלא אושר לא יקבל שורה אחת, גם אם ישנה את הקוד בדפדפן.
2. הגישה היא **קריאה בלבד** — אין שום מדיניות שמאפשרת למאמן לכתוב
   אצל המתאמן.
3. ברגע שהמתאמן לוחץ «ביטול גישה», הסטטוס עובר ל־`revoked` והקריאה
   הבאה נחסמת. אין צורך שהמאמן יסגור משהו.

**מה שכן חשוב לדעת:** אישור הוא הכל-או-כלום. מאמן מאושר קורא את כל
מפתחות ה־`app_data` של המתאמן — יומן, משקל, ופרטי הפרופיל. אם תרצה
הפרדה עדינה יותר, זה שינוי בסכימה: לפצל את המפתחות לרמות רגישות
ולסנן במדיניות לפי `key`.

טבלת `profiles` קריאה לכל משתמש מחובר, כי בלי זה אי אפשר לחפש לפי שם
משתמש. היא חושפת שם משתמש, שם תצוגה ותפקיד בלבד — לא נתוני תזונה.

### שדרוג ממסד קיים

`schema.sql` idempotent, אז פשוט הרץ אותו שוב ב-SQL Editor. הוא יוסיף את
`profiles` ו־`coach_links` ואת המדיניות החדשה בלי לגעת בנתונים הקיימים.
משתמש שנרשם לפני השינוי לא יופיע בחיפוש עד שייצור שם משתמש — הכי פשוט
לצאת ולהירשם מחדש, או להוסיף לו שורה ב־`profiles` ידנית.

## צ׳אט

לכל קישור מאושר יש שיחה. המאמן פותח אותה מרשימת המתאמנים או מתוך
התצוגה החיה; המתאמן פותח אותה מבלוק «בקשות מאמנים» במסך הפרופיל.

* ההודעות נטענות מחדש כל 5 שניות בזמן שהחלון פתוח, ורק החדשות נמשכות
  (`created_at=gt.<אחרונה>`), אז זו בקשה קטנה ולא טעינה מלאה.
* **קריאה** מותרת לשני הצדדים של הקישור גם אחרי ביטול גישה — היסטוריית
  שיחה לא נמחקת בלי שמישהו ביקש.
* **שליחה** מותרת רק כל עוד הקישור במצב `approved`. ברגע שהמתאמן מבטל,
  ההודעה הבאה נדחית ב-RLS, והאפליקציה מציגה «אין הרשאה לשלוח».

זה פולינג, לא Realtime. אם תרצה דחיפה מיידית במקום כל 5 שניות, Supabase
Realtime עושה את זה עם מנוי לטבלת `messages` — שינוי של כמה שורות
ב-`cloud.js` בלבד, בלי נגיעה בסכימה.

**שים לב:** את `schema.sql` צריך להריץ שוב, הוא מוסיף את טבלת `messages`
ואת המדיניות שלה.

## ביטול גישה ובקשה חוזרת

מתאמן שמבטל מאמן מעביר את הקישור ל-`revoked`. השורה נשארת — היא נושאת
את היסטוריית השיחה — אבל היא לא נחשבת קישור פעיל:

* המאמן לא רואה את המתאמן ברשימה, ולא קורא את הנתונים שלו.
* בחיפוש, המתאמן חוזר להיות זמין עם כפתור «בקשה חוזרת».
* בקשה חוזרת היא upsert על האילוץ `(coach_id, trainee_id)` שמחזיר את
  הסטטוס ל-`pending`. בלי `on_conflict` מפורש, PostgREST היה מנסה
  INSERT ונופל על 409.

### תיקון אבטחה בגרסה הזאת

מדיניות העדכון על `coach_links` הייתה אחת לשני הצדדים, ולכן אפשרה
למאמן לשלוח `PATCH status=approved` ולאשר את עצמו. היא פוצלה:

```sql
create policy "trainee decides link" on public.coach_links
  for update using (auth.uid() = trainee_id) with check (auth.uid() = trainee_id);

create policy "coach requests or cancels" on public.coach_links
  for update using      (auth.uid() = coach_id)
             with check (auth.uid() = coach_id and status in ('pending','revoked'));
```

המאמן יכול רק לבקש מחדש או להסיר את עצמו. `approved` אינו באפשרויות
שלו — האישור שייך למתאמן בלבד, ונאכף במסד.

**חובה להריץ את `schema.sql` שוב** כדי שהתיקון ייכנס לתוקף.

## איך לדעת איזו גרסה רצה אצלך

בתחתית מסך הפרופיל מופיע מספר גרסה, והוא נרשם גם לקונסול בטעינה.
אם המספר שם נמוך ממה שהעלית — הדפדפן מריץ קוד ישן מה-cache, וכל
תיקון שתחפש לא יהיה שם.

### מה שונה ב-service worker

עד עכשיו כל הקבצים היו cache-first, כולל `app.js`. זה מהיר, אבל אומר
שעדכון קוד נכנס לתוקף רק אחרי מחזור חיים שלם של ה-SW. עכשיו הקוד עצמו
(`.js`, `.html`, `.webmanifest`) נטען **רשת קודם** עם ה-cache כגיבוי,
ושאר הנכסים — אייקונים, הסורק — נשארו cache-first.

התוצאה: עדכון נכנס בטעינה הראשונה שיש בה אינטרנט, והאפליקציה עדיין
עובדת אופליין.

### אם משהו עדיין נראה ישן

1. באייפון, אם התקנת למסך הבית: מחק את האייקון והתקן מחדש.
   service worker בתוך אפליקציה מותקנת לא מתעדכן מרענון בספארי.
2. בדפדפן: `F12 → Application → Service Workers → Unregister`, ואז
   `Ctrl+Shift+R`.

## אם בקשת גישה נכשלת

במסך הפרופיל, תחת «חשבון וסנכרון», יש כפתור **בדיקת חיבור**. הוא מדווח
שרת מוגדר, מחובר, שם משתמש, **תפקיד**, מספר קישורים, גרסה, וכל שגיאה
שהמסד מחזיר. זו התשובה במקום ניחוש.

### התפקיד הוא החשוד הראשון

מדיניות ההוספה ל-`coach_links` דורשת שהמבקש יהיה מסומן כמאמן:

```sql
and exists (select 1 from public.profiles p
            where p.user_id = auth.uid() and p.role = 'coach')
```

חשבון שנוצר לפני שהוספנו את בחירת התפקיד, או שנשמר עם ברירת המחדל,
יקבל 403 בלי הסבר. לכן נוסף **מחליף סוג חשבון** באותו בלוק — לחיצה
אחת מעדכנת את `profiles.role`.

### מה שונה בשליחת הבקשה

הקריאה השתמשה ב-upsert עם `on_conflict=coach_id,trainee_id`. זו תבנית
עדינה: היא תלויה בכך שהשרת יזהה את האילוץ בדיוק, ונכשלת בצורה לא ברורה
כשלא. במקומה הקוד בודק אם כבר קיימת שורה, ואז מבצע `PATCH` להחזרת
הסטטוס ל-`pending`, או `POST` רגיל אם אין. שתי הקריאות נשענות על
מדיניות פשוטה ומפורשת.

## באג שכדאי לזכור: hidden מול display

התכונה `hidden` מיושמת על ידי הדפדפן ככלל `[hidden]{display:none}`
בגיליון ברירת המחדל. **כל** כלל מפורש בגיליון שלך גובר עליו, כי
ספציפיות של מחלקה גבוהה יותר. התוצאה: אלמנט עם `class="form"`
(`display:grid`) נשאר גלוי גם כש-JS מסתיר אותו.

זה מה שגרם לטופס האימייל והסיסמה להישאר על המסך אחרי התחברות.
הפתרון הוא כלל אחד:

```css
[hidden]{display:none!important}
```

האלמנטים שהיו מושפעים: `#acctOut`, `#acctIn`, `#roleRow`. שאר הפאנלים
(`#onb`, `#chatPanel`, `#scrim`) לא נפגעו כי כתבתי להם כלל `[hidden]`
ייעודי מלכתחילה — מה שהסתיר את הבאג במקום לחשוף אותו.

## צ׳אט: מהירות ותמונות

### למה הייתה תחושת דיליי

השליחה עשתה שני סיבובים לשרת — POST ואז טעינה מחדש — והפולינג היה
כל 5 שניות. עכשיו:

* **שליחה אופטימית** — הבועה מופיעה מיד והתיבה מתרוקנת מיד, לפני
  שהרשת בכלל נגעה בזה. השרת רק מאשר.
* `Prefer: return=representation` מחזיר את השורה שנוצרה, כולל
  `created_at` האמיתי. אין סיבוב שני.
* **פולינג מתכוונן** — כל 2 שניות בזמן שיחה פעילה, יורד ל-6 שניות
  אחרי 15 סבבים ריקים, וחוזר ל-2 ברגע ששולחים.
* אם השליחה נכשלת, הבועה נצבעת ומקבלת כפתור «נסה שוב» — ההודעה לא
  נעלמת ולא חוזרת לתיבת הכתיבה.

זה עדיין פולינג. Supabase Realtime ייתן דחיפה מיידית עם מנוי לטבלת
`messages`, וזה שינוי מקומי ב-`cloud.js` בלבד.

### תמונות

* צילום או בחירה מהגלריה, הקטנה ל-1200px ו-JPEG באיכות 0.75 לפני
  ההעלאה — תמונת טלפון היא 3–6MB וזה מיותר בצ׳אט.
* הקובץ עולה לדלי **פרטי** בשם `chat`, בנתיב `<link_id>/<קובץ>`.
* הצפייה היא דרך קישור חתום לשעה. אין URL ציבורי לתמונות.
* מדיניות האחסון נשענת על אותו נתיב:

```sql
create policy "link members read chat images" on storage.objects
  for select to authenticated
  using (bucket_id = 'chat' and exists (
    select 1 from public.coach_links l
    where l.id::text = (storage.foldername(name))[1]
      and (l.coach_id = auth.uid() or l.trainee_id = auth.uid())));
```

העלאה מותרת רק כשהקישור `approved`; קריאה מותרת לחברי הקישור גם אחרי
ביטול, בדיוק כמו בהודעות הטקסט.

**חובה להריץ את `schema.sql` שוב** — הוא מוסיף את עמודת `image_path`,
את הדלי ואת מדיניות האחסון.

## תוכניות אימון

### מאמן

בתצוגת המתאמן וברשימת המתאמנים יש כפתור **תוכנית אימונים**. הפאנל
נפתח על שבעה ימים; לכל יום מוסיפים תרגילים עם סטים, חזרות, מנוחה
והערה, ואפשר להעתיק יום שלם ליום אחר. יום בלי תרגילים הוא יום מנוחה.
התוכנית נשמרת כ-`jsonb` אחד לכל קישור.

### מתאמן

מסך «התקדמות» חולק לשלוש קטגוריות:

* **ההתקדמות שלי** — מה שהיה שם עד עכשיו.
* **האימונים שלי** — התוכנית לפי ימים. ביום הנוכחי יש תיבת סימון לכל
  תרגיל, פס התקדמות, וסרגל של שבעת הימים האחרונים.
* **חברים** — ריק בכוונה, מוכן להמשך.

סימון ביצוע אפשרי **ביום עצמו בלבד**. דיווח למפרע הופך את המעקב
לחסר ערך למאמן.

### חלוקת הבעלות

```sql
create policy "coach writes plan"   on workout_plans for insert with check (auth.uid() = coach_id ...);
create policy "trainee writes logs" on workout_logs  for insert with check (auth.uid() = trainee_id);
```

המאמן כותב תוכניות ולא יכול לסמן ביצוע. המתאמן מסמן ביצוע ולא יכול
לשנות את התוכנית. שניהם קוראים את שניהם. זה נאכף במסד.

בתצוגה החיה המאמן רואה שורה נוספת: «אימון היום: בוצע» או כמה תרגילים
סומנו מתוך כמה.

**חובה להריץ את `schema.sql` שוב** — הוא מוסיף את `workout_plans`,
`workout_logs` והמדיניות שלהן.

## מאגר התרגילים

`exercises.js` — 87 תרגילים בעברית, כל אחד עם שריר יעד, ציוד, שם באנגלית
לחיפוש, ודגש טכני קצר. המאגר בקוד, לא ב-API, אז הוא עובד אופליין ואין
תלות בשירות חיצוני.

בעורך התוכנית יש כפתור **בחירה מהמאגר**: חיפוש חופשי (עברית או אנגלית),
סינון לפי שריר, וסינון לפי ציוד. בחירת תרגיל ממלאת את השם ומכניסה את
הדגש הטכני לשדה ההערה. אפשר גם להקליד שם חופשי, למי שיש תרגיל משלו.

### למה מפת שרירים ולא צילום

סטים של איורי אימון או צילומי תרגילים הם חומר מוגן בזכויות יוצרים.
במקום זה `muscleMapSVG()` מייצר צללית גוף ומדגיש בה את השריר שהתרגיל
עובד עליו — מבט מלפנים לחזה, בטן, כתפיים, יד קדמית ורגליים, ומבט מאחור
לגב, יד אחורית, ישבן וירך אחורית.

זה נוצר בקוד: אין קבצי תמונה, אין בקשות רשת, וזה מסתגל אוטומטית
לצבעי הערכה. גם יותר שימושי מצילום, כי מה שחשוב בבחירת תרגיל הוא
איזה שריר הוא עובד.

אם בהמשך תרצה צילומים אמיתיים, `wger.de` מציע API פתוח עם תמונות
ברישיון חופשי — זו תוספת של שדה `image` לכל שורה ושליפה עצלה.

### הוספת תרגילים

זה מערך פשוט בראש `exercises.js`:

```js
{n:'שם בעברית', en:'english for search', m:'chest', eq:'barbell', d:'דגש טכני'}
```

מפתחות השרירים והציוד מוגדרים ב-`MUSCLES` ו-`EQUIP` באותו קובץ.


### אם החיפוש במאגר לא נפתח

`exercises.js` הוא קובץ נפרד. אם הוא לא הועלה לריפו, או שקובץ
`index.html` ישן מה-cache הוגש בלי תג הסקריפט שלו, `EXERCISES` לא
מוגדר והלחיצה על «בחירה מהמאגר» נכשלת בלי הודעה.

שלוש הגנות נוספו:

1. הקוד מנסה לטעון את `exercises.js` בעצמו אם הוא חסר.
2. אם עדיין אין — מופיעה הודעה מפורשת במקום כלום.
3. **בדיקת חיבור** במסך הפרופיל מדווחת «מאגר תרגילים: 87» או
   «חסר — exercises.js לא נטען».

בנוסף, שדה שם התרגיל הפך לחיפוש בעצמו: הקלדה של שתי אותיות מציגה עד
שש הצעות עם מפת שרירים, ולחיצה עליהן ממלאת את השם ואת הדגש הטכני.
זה מה שמשתמש מנסה קודם, לפני שהוא מחפש כפתור.

**ודא שהקובץ עלה:** בריפו צריך להופיע `exercises.js` לצד `app.js`.


### הבורר, בגרסה הסופית

שדה ההקלדה החופשית ירד. לחיצה על שדה התרגיל פותחת פאנל מלא:

* כותרת עם X לסגירה ו-**יצירה** להוספת תרגיל אישי
* שורת חיפוש עם אייקון זכוכית מגדלת
* שתי שורות צ׳יפים — שרירים וציוד. הצ׳יפ הפעיל לבן.
* רשימה עם מפת שרירים משמאל, שם ותת-כותרת «שריר · ציוד» מימין

**יצירה** שומרת תרגיל אישי מקומית תחת `maazan:customex`. הוא מופיע
בראש הרשימה עם התווית «התרגיל שלי», ומתנהג ככל תרגיל אחר — כולל מפת
שרירים לפי מה שבחרת.

החיפוש עובד על שם בעברית, שם באנגלית, שם השריר ושם הציוד. הקלדת
«ידיים» תביא תרגילי יד קדמית ואחורית.


### שני באגים בפאנלים, ומה גרם להם

**הבורר נפתח מתחת לפאנל התוכנית.** שניהם `.chat` עם `z-index:75`,
והבורר מופיע לפניו ב-DOM — אז פאנל התוכנית נצבע מעליו. הלחיצה על
«חיפוש» עבדה כל הזמן; פשוט לא היה מה לראות עד שסגרת את התוכנית.
התיקון: `.picker{z-index:78}`.

מפת השכבות המלאה, כדי שזה לא יחזור:

| שכבה | z-index |
|---|---|
| topbar | 20 |
| tabbar / fab | 30 / 31 |
| scrim (sheet) | 50 |
| toast | 60 |
| cam | 70 |
| chat / plan | 75 |
| picker | 78 |
| onboarding | 80 |
| lightbox | 90 |

**הרשימה לא נגללה.** ב-flex column, אזור גלילה פנימי צריך ש**כל** אב
בדרך יהיה `flex:1` עם `min-height:0`. `#pickBrowse` היה div רגיל בלי
שניהם, ולכן `.planbody` שבתוכו לא ידע לחשב גובה. אותו כלל הוחל גם על
שורות הצ׳יפים, עם `-webkit-overflow-scrolling:touch` לגלילה חלקה
באייפון.
